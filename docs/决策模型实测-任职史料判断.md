# 决策模型实测（二）：判断《明实录》一段是否任职史料

> 2026-10-18 晚。接 [决策模型实测.md](决策模型实测.md) 的结论继续压测。
> 脚本：`_scratch/systemone/shilu_probe2.py`；原始数据：`_scratch/systemone/shilu_out2.json`。
> 文本池是项目真实数据 `src/mingoff/data/sinica_all.json`（502 人 / 27,544 条），随机抽样 30 段。

## 一、问法与口径

每段文本一次请求，问两个问题：

1. `noul`「这段文字是否在记载某人获得、转任、兼任或失去官职？」
2. `choice`「记载了哪种任职情况？」（初授/升迁/改调/兼任/致仕/罢免/起复/其他/否）

两套问法对照：

- **冷问（cold）**：只给问句，不给判断标准 → 测它自己的史识；
- **热问（hot）**：把《数据接入规范》的判据写进 instructions（"只有明确写出授/陞/改/調/補某一实职，
  或明确记载离任才算；议论、举荐、请求、议罪、行政事务不算"）→ 测它**按标准执行**的能力。

另做一组对照：把人名替换成「某甲」，同一文本再问一次。

## 三、三个能用的结论

### 3.1 它能认出"记载明确"的任命，但不认"按标准硬判"

- **魏校**（"陞太常寺少卿魏校為本寺卿"）：冷 0.99 / 热 0.85，方式判"升迁" —— 对，且稳。
- **謝遷**（"授少傅兼…戶部尚書…謝遷階光祿大夫"）：0.96，方式判"兼任" —— 对。
- **蕭良有**（"以修撰蕭良有充編纂章奏官"）：0.97 —— 对，但方式判"其他"，**没有识别出这是"以本职充某差"**。

### 3.2 它不会照准则把"议论/举荐/奏疏"划到否定

热问把标准写清楚以后：P(yes) 均值从 0.26 **升到 0.44**，骑墙从 7 段涨到 20 段。
一段纯御史言官奏疏（#16 張至發"請議定滅奴賞格…"），冷问 0.03（对），热问反而 0.50（错）。
**给它规则，它更容易判"是"，而不是更准。** 这与我之前"它随提示走"的结论一致：
instructions 里出现的"授予/陞/改"等字眼，会把它的决策往上推。

### 3.3 单段里"沾边即答"，分不清主体

**#10 許讚**：原文明说"大學士夏言顧鼎臣翟鑾及吏部尚書許讚而下各疏引咎乞罷**俱溫旨諭留**，
独刑部尚書周期雍**准致仕**"。正确结论是：许讚**没有被致仕**，被准致仕的是周期雍。
模型 cold/hot 两次都答「致仕」（0.32 / 0.33）。它抓住了"致仕"词，但**没分清主体**。
这类"多人同句、各殊结局"的记载，正是年表/实录校勘里最容易出错的地方。

## 四、对照实验：抹掉人名后作答几乎不变

| # | 冷问 P(yes) | 抹名后 P(yes) | 判方式 |
|---|---|---|---|
| 0 | 0.46 | 0.56 | 其他 → 其他 |
| 1 | 0.40 | 0.31 | 其他 → 其他 |
| 2 | **0.96** | **0.96** | 兼任 → 兼任 |
| 3 | 0.21 | 0.21 | 其他 → 其他 |
| 4 | 0.01 | 0.03 | 其他 → 其他 |
| 5 | 0.65 | 0.64 | 其他 → 其他 |
| 6 | **0.99** | **0.99** | 升迁 → 升迁 |
| 7 | 0.20 | 0.16 | 兼任 → 兼任 |

**它判的是"文本形态"（有没有"陞…為…"这种句式），不是"谁任了什么"。**
这对"是否任职史料"这个二元判断够用，对"这段记载的是谁的哪一次任职"完全不够。

## 五、对项目的实用结论

| 问题 | 结论 |
|---|---|
| 能当"是否任职史料"的粗筛吗？ | **能，但当不了最终判据**：30 段里 20 段判否（冷问）大体正确，但正确的判是把它当"句式过滤器"，而且只应接受 >0.9 的高分判定，其余交规则。 |
| 能判"怎样任职"吗？ | **部分能**：升迁 / 兼任在"句式明确"时能判对；"以本职充差""恩蔭""加官""起复"分不清；多人同句必错主体。 | 
| 能替代项目里的规则吗？ | **不能**：项目里 `shilu.py` + `buyuan_repair.py` 的注文解析是逐字定位到人，模型给不了这层粒度（第四节已证）。 |
| 能替代原书页核吗？ | **不能**：它不看图，也不查史实。 |
| 可以怎么用（限时免费期间可试） | ① 对**已有规则命中**的条目做"二次复核"（只当低分否决器）；② 给"疏言/奏议"类做**粗分类打标**，例如标"奏疏/任命/致仕/卒谥/其他"，供人工筛选；③ 做**抽样质检**：从 3,000+ 条里挑出它判"不确定"的，优先回原书看。 |

## 六、工程坑（第二次踩到，记下来）

- **不要在同一个请求里把问题 id 加前缀（如 `t0_is_tenure`）**：返回的 `answers` 里键名会被截短或丢失，
  实测多问长 id 时 `noul` 直接返回 `{}`。**一次请求只放一段文本 + 简短问题 id**（`is` / `how` 即可）。
- 一次 30 段 × 2 问 = **17,804 input tokens**，延迟 150–400 ms/次；限时免费期间成本可忽略。
- 键名带下划线没事，长 id（>10 字符）+ 中文问题组合最容易失败；失败时**不报错**，静默返回空对象，
  必须校验 `answers` 非空。
