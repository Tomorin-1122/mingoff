## D3. schema 变更策略：暂不做自动迁移

**背景**：`CREATE TABLE IF NOT EXISTS` 对已存在的表不会改结构。

**决策**：`meta.schema_version` 记录版本；阶段① 允许**重建库**（数据量小、
可由 seed 重放）。不引入 Alembic。

**理由**：MVP 阶段数据可从来源重放，迁移工具是过早优化。

**代价**：一旦开始手工录入校勘成果（不可重放的数据），必须补迁移机制。
**这是进入阶段② 前必须还的债。** 判断标准：当"库里有任何不能由脚本重放的
数据"时，立即停手先做迁移。

## D4. `NULL` 表示"史料未载"，绝不用 0

**背景**：史料常缺载生卒年、任职起止年。

**决策**：所有"未载"一律 `NULL`。显示时渲染为 `?`。

**理由**：`0` 会被读成真实数值（"生于公元 0 年""任期从第 0 年开始"），
且**统计时会静默出错**——例如算平均任期会把未载年当成 0 年拉低均值。
这类错误很难发现，代价却直接落在论文结论上。

**代价**：所有聚合查询都要显式处理 `NULL`（`WHERE start_year IS NOT NULL`）。
这是**必要的麻烦**——它逼着写查询的人想清楚"未载的记录要不要算进去"。

## D5. 任职类型必须是受控词表

**背景**：PRD 要求区分实授/署理/加衔。

**决策**：`tenure_type` 用 `CHECK` 约束在 5 个值内。

**理由**：这不是格式洁癖，是**事实区分**：
- 兵部尚書 = 实授
- 權兵部尚書 = 署理
- 兵部尚書銜 = 加衔（督师/总督带衔，**不是京中兵部尚书**）

混同会让"历任兵部尚书"的统计把袁崇焕、卢象升算进去——而 PRD 12.2 明确
要求排除他们。`CHECK` 让打错字无法静默入库。

**代价**：新增类型要改 schema。

## D6. 去重按 (姓名 + 籍贯)，不按姓名

**背景**：反复导入 CBDB 快照/年表是常态，重复导入不该让数据翻倍。

**决策**：
- 有 `cbdb_id` → 按 cbdb_id 去重；
- 无 `cbdb_id` → 按 (姓名, 籍贯) 去重。

**理由**：只按姓名去重有**误合并**风险——明代同名者众，两个"張三"很可能是
两个人。误把两个人合成一个，比留两份（可后续人工合并）严重得多。
籍贯提供额外区分维度。

**代价**：同一人籍贯记载有异时会留两份。可接受——这正是 `discrepancy` 表
该处理的情况。

**由来**：这条例外是实测发现的——早期版本只在有 cbdb_id 时去重，而种子数据
没有 cbdb_id，重复 seed 直接把 14 人变成 28 人。测试
`test_seed_is_additive_not_duplicating` 守住它。

## D7. 任职去重包含 end_year

**决策**：`(person, office, start_year, end_year, tenure_type)` 全同才算重复。

**理由**：粗到只看 `(person, office, start_year)` 会把**连任**抹平——
同一人在同一职位上 1630–1632 与 1630–1635 是两条不同的记载（期限不同，
很可能是异文或续任），合并会丢信息。

**代价**：同一任命的细微记载差异会留两条。由 `discrepancy` 收口。

## D8. 快照对 `NULL` 采取"宁可多列"策略

**决策**：某年快照中，`start_year IS NULL` 或 `end_year IS NULL` 的记录
**都算在任**。

**理由**：历史数据缺载是常态。漏列一条（该在朝堂名单里却没出现）比多列一条

**代价**：快照可能包含实际未在任的人。UI 上应标注"任职时间未载"。

## D11. 双许可：代码 MIT/Apache + 数据 CC BY-NC-SA 4.0

**背景**（实测 `cbdb-project/cbdb_sqlite/LICENSE.md`）：

> CBDB SQLite 数据库适用 CBDB 資料授權條款（2026-08-20 生效）：在当前单机版
> 发布日期当日或之前发布、且在其数据量范围内者仍适用 **CC BY-NC-SA 4.0**，
> 其餘適用 CBDB 自訂條款。

**决策**（2026-10-16 老板拍板）：

| 层 | 许可 | 说明 |
|---|---|---|
| **代码** | Apache-2.0 | 宽松，便于学术协作与二次开发 |
| **本项目自整理的数据** | CC BY-NC-SA 4.0 | 与 CBDB 同轨，避免混许可 |
| **CBDB 衍生数据** | CC BY-NC-SA 4.0 | 必须署名 + 非商业 + 相同方式共享 |

**理由**：CC BY-NC-SA 的 ShareAlike 有传染性——用了 CBDB 的衍生库必须以同许可发布。
把它**限制在数据层**、代码层用宽松许可，是开源项目的通行做法，也让"代码可被
自由复用"这一卖点不被数据许可拖住。

**代价与纪律**：
1. 每个数据文件要有独立的许可头/元数据，**不能让 grep 一个 LICENSE 就以为全站宽松**；
2. 导入 CBDB 的每个批次记录**快照日期**（如 `cbdb_20261010`），以便判断适用哪套条款；
3. **非商业**是硬约束 —— 站点不得接广告、不得卖数据、不得做付费墙。

**触发点**：若将来要商业化，CBDB 衍生部分必须剥离或另行取得授权。

## D16. 时间轴：每年 12 个月等宽；皇帝行置顶；只保留一条时间轴

**背景**（2026-10-16 老板反馈）：

> "皇帝这一行应该在最顶上，你怎么跑到最下面了？"
> "你这时间轴有两条，非常复杂，还是简洁一点好了"
> "还是每年都要有12个月的刻度，每年的长度要一样，这样美观一点，跑起来也比较直观"

**决策**：

1. **皇帝行置顶** —— 原来错放在表格最底；它是"背景坐标"，理应在所有职官之上；
2. **只保留一条时间轴** —— 原来页头一个滑块条 + 图表内一个年轴，重复且混乱。
   现在：滑块留在页头属"视图控件"，**年轴并入图表**（与表格同处一条轴上，
   所以必然对齐、也必然一起滚动）；
3. **按月等宽**：每年固定 12 格，17 年 = 204 格。各年长度完全一致。

**代价**：年格变窄（约 18px/年），干支无法逐年标注 —— 改为只在元年/十年/末年显示。

## D28. 年份头错位的修复与审计（2026-10-18）
