# 设计决策记录（ADR）

记录"为什么这样做"，避免后来者（包括几个月后的自己）重复论证或误改。
每条格式：背景 → 决策 → 理由 → 代价。

---

## D1. 用 SQLite，不用 PostgreSQL（与 PRD 建议不同）

**背景**：PRD 第 8 节建议 PostgreSQL。

**决策**：MVP 阶段用 SQLite，schema 全部用标准 SQL 写。

**理由**：阶段① 是单人开发，数据量 14 条任职。PostgreSQL 带来的部署成本
（安装、起服务、连接管理、备份）在验证数据模型阶段是纯负担。

**代价**：迁移时要改连接层。为此做了两件事对冲：① schema 不用 SQLite 专属语法
（部分索引用 `WHERE`，PG 也支持）；② 所有 SQL 集中在 `repo.py`，迁移只改这一层。

**何时该迁移**：进入阶段③（全朝中层）或需要并发写时。

---

## D2. 不用 ORM

**背景**：SQLAlchemy 是 Python 数据层默认选择。

**决策**：手写 SQL + dataclass。

**理由**：只有 6 张表，查询以只读统计为主。更重要的是——**本项目最需要小心的
是 `NULL` 语义**（史料未载 vs 记载为零），而 ORM 会把 `NULL` 与默认值之间的
区别藏起来。裸 SQL 里 `COALESCE(start_year,-1)` 这种写法是**看得见**的。

**代价**：没有自动迁移工具。当前靠 `CREATE TABLE IF NOT EXISTS`；
真要改 schema 时需要手写迁移（见 D3）。

---

## D3. schema 变更策略：暂不做自动迁移

**背景**：`CREATE TABLE IF NOT EXISTS` 对已存在的表不会改结构。

**决策**：`meta.schema_version` 记录版本；阶段① 允许**重建库**（数据量小、
可由 seed 重放）。不引入 Alembic。

**理由**：MVP 阶段数据可从来源重放，迁移工具是过早优化。

**代价**：一旦开始手工录入校勘成果（不可重放的数据），必须补迁移机制。
**这是进入阶段② 前必须还的债。** 判断标准：当"库里有任何不能由脚本重放的
数据"时，立即停手先做迁移。

---

## D4. `NULL` 表示"史料未载"，绝不用 0

**背景**：史料常缺载生卒年、任职起止年。

**决策**：所有"未载"一律 `NULL`。显示时渲染为 `?`。

**理由**：`0` 会被读成真实数值（"生于公元 0 年""任期从第 0 年开始"），
且**统计时会静默出错**——例如算平均任期会把未载年当成 0 年拉低均值。
这类错误很难发现，代价却直接落在论文结论上。

**代价**：所有聚合查询都要显式处理 `NULL`（`WHERE start_year IS NOT NULL`）。
这是**必要的麻烦**——它逼着写查询的人想清楚"未载的记录要不要算进去"。

---

## D5. 任职类型必须是受控词表

**背景**：PRD 要求区分实授/署理/加衔。

**决策**：`tenure_type` 用 `CHECK` 约束在 5 个值内。

**理由**：这不是格式洁癖，是**事实区分**：
- 兵部尚書 = 实授
- 權兵部尚書 = 署理
- 兵部尚書銜 = 加衔（督师/总督带衔，**不是京中兵部尚书**）

混同会让"历任兵部尚书"的统计把袁崇焕、卢象升算进去——而 PRD 12.2 明确
要求排除他们。`CHECK` 让打错字无法静默入库。

**代价**：新增类型要改 schema。

---

## D6. 去重按 (姓名 + 籍贯)，不按姓名

**背景**：反复导入 CBDB 快照/年表是常态，重复导入不该让数据翻倍。

**决策**：
- 有 `cbdb_id` → 按 cbdb_id 去重；
- 无 `cbdb_id` → 按 (姓名, 籍贯) 去重。

**理由**：只按姓名去重有**误合并**风险——明代同名者众，两个"張三"很可能是
两个人。误把两个人合成一个，比留两份（可后续人工合并）严重得多。
籍贯提供额外区分维度。

**代价**：同一人籍贯记载有异时会留两份。可接受——这正是 `discrepancy` 表
该处理的情况。

**由来**：这条例外是实测发现的——早期版本只在有 cbdb_id 时去重，而种子数据
没有 cbdb_id，重复 seed 直接把 14 人变成 28 人。测试
`test_seed_is_additive_not_duplicating` 守住它。

---

## D7. 任职去重包含 end_year

**决策**：`(person, office, start_year, end_year, tenure_type)` 全同才算重复。

**理由**：粗到只看 `(person, office, start_year)` 会把**连任**抹平——
同一人在同一职位上 1630–1632 与 1630–1635 是两条不同的记载（期限不同，
很可能是异文或续任），合并会丢信息。

**代价**：同一任命的细微记载差异会留两条。由 `discrepancy` 收口。

---

## D8. 快照对 `NULL` 采取"宁可多列"策略

**决策**：某年快照中，`start_year IS NULL` 或 `end_year IS NULL` 的记录
**都算在任**。

**理由**：历史数据缺载是常态。漏列一条（该在朝堂名单里却没出现）比多列一条
（可能是误报）更难发现——前者会被当成"这人当时确实不在任"。

**代价**：快照可能包含实际未在任的人。UI 上应标注"任职时间未载"。

---

## D9. 数据层先行，可视化后置

**背景**：PRD 5.3 列了时间轴/甘特/朝堂快照/关系网四种可视化。

**决策**：阶段① 先只做数据层与 CLI，一行前端代码都不写。

**理由**：可视化的价值完全依赖数据正确性。在 `NULL` 语义、去重规则、
任职类型区分都没验证过的时候就做图表，只会把错误数据画得更好看。

**代价**：MVP 交付物目前是 CLI 而非网页，与 PRD 阶段① 的"可访问的网页原型"
尚有距离。**这是已知的、有意的差距。**

---

## D10. 不把明实录全文搬进本库

**背景**：父项目 `guji-pipeline` 已能直接抓识典《明實錄》全文（书 ID `LS0026`，
3118 章，实测可行）。

**决策**：本库只存**引用信息**（书名/卷次/URL），不存全文正文。
查询与核对通过父项目的 CLI 现取现用。

**理由**：PRD 4.3 自定的合规硬约束——识典内容是平台的整理成果，
批量搬运有条款风险。而"现取现核"在论文查证场景（一次查几卷）成本极低。

**代价**：离线时无法核对原文。可接受——核对本来就该在有网络时做。

## D11. 双许可：代码 MIT/Apache + 数据 CC BY-NC-SA 4.0

**背景**（实测 `cbdb-project/cbdb_sqlite/LICENSE.md`）：

> CBDB SQLite 数据库适用 CBDB 資料授權條款（2026-08-20 生效）：在当前单机版
> 发布日期当日或之前发布、且在其数据量范围内者仍适用 **CC BY-NC-SA 4.0**，
> 其餘適用 CBDB 自訂條款。

**决策**（2026-10-16 老板拍板）：

| 层 | 许可 | 说明 |
|---|---|---|
| **代码** | Apache-2.0 | 宽松，便于学术协作与二次开发 |
| **本项目自整理的数据** | CC BY-NC-SA 4.0 | 与 CBDB 同轨，避免混许可 |
| **CBDB 衍生数据** | CC BY-NC-SA 4.0 | 必须署名 + 非商业 + 相同方式共享 |

**理由**：CC BY-NC-SA 的 ShareAlike 有传染性——用了 CBDB 的衍生库必须以同许可发布。
把它**限制在数据层**、代码层用宽松许可，是开源项目的通行做法，也让"代码可被
自由复用"这一卖点不被数据许可拖住。

**代价与纪律**：
1. 每个数据文件要有独立的许可头/元数据，**不能让 grep 一个 LICENSE 就以为全站宽松**；
2. 导入 CBDB 的每个批次记录**快照日期**（如 `cbdb_20261010`），以便判断适用哪套条款；
3. **非商业**是硬约束 —— 站点不得接广告、不得卖数据、不得做付费墙。

**触发点**：若将来要商业化，CBDB 衍生部分必须剥离或另行取得授权。

## D12. 不用引得数字人文平台

**背景**：引得平台（`www.inindex.com`）收录「中国历代职官数据库」，与本项目高度
重合，但**需机构 IP 登录**，且属商业数据平台。

**决策**（2026-10-16 老板拍板）：**不使用**。

**理由**：本项目定位为**开源非商业**项目。引入商业数据源会在许可与分发上产生
不可控约束（无法验证其条款是否允许衍生发布），与开源定位冲突。

**代价**：失去一个现成的职官数据源。改用公开史料（《明史》七卿年表/宰辅年表、
CBDB 官方快照、中研院公开检索）自建。

## D13. 「大明职官图」定位为借鉴对象，不是敌人

**背景**：实测竞品 `dingbo3603-ui/ming-official-atlas`（2026-09-07 上线，321 MB）
已实现本项目 PRD 设想的多数功能。

**决策**（2026-10-16 老板判断）：它**应为历史学工作者借助 AI 写成的项目**，
本项目把它当作**借鉴对象**而非竞争对象。

**理由**：
1. 它**没有 LICENSE**，其 CBDB 改编数据自述为 CC BY-NC-SA 4.0 却未随仓库提供
   完整许可文件——**许可状况不清**，不宜直接采用其数据；
2. 其数据整理脚本「还依赖本地原始资料目录和数据库导出」，**不可复现**；
3. 同为明代职官研究，彼此可参考的是**问题意识与呈现方式**，而非数据本身。

**可借鉴的点**（记录备查）：
- 把「首辅、掌府、协理等实际职事与本衔、兼衔分开记录」——比我们的
  `tenure_type` 三分类更细，值得参考是否需要区分"实际职事"维度；
- 「完全无日期的资料进入'尚未明确系年'分组，**不填入年度**」——与我们的
  `NULL ≠ 0` 原则一致，是独立得出的相同结论；
- 地图与州县衙署场景——超出本项目一期范围，但验证了"空间维度"有需求。

## D14. 核心竞争点：按年的职官可视化

**背景**：老板明确定位。

**决策**：
- **核心竞争点是"按年的职官可视化"** —— 拖到某一年，就看清楚那一年谁在任；
- 项目为**开源非商业**，**预计上线网站**；
- 一期**先做可视化原型**（用现有种子数据），验证交互效果后再扩数据。

**理由**：竞品的可视化偏"地图 + 场景"，本项目切**时间轴**这一条线做深。
明代职官研究最实际的需求是"某年谁掌什么"，而现有工具（含 CBDB）都以
**人物**为入口，按年横切是真实缺口。

**代价**：先做原型意味着数据尚薄（现仅兵部尚书 14 条）。**这是有意的**——
老板要先审视交互效果再决定投入方向。

## D15. 断限：止于崇祯十七年三月北京城陷落，不做南明

**背景**：崇祯十七年三月十九日（1644-04-25）李自成入京，此后为南明弘光朝。

**决策**（2026-10-16 老板拍板）：**排除** 1644 年三月之后的任命与弘光朝人物。

**理由**：上一版把南明任命降置信度保留，但降置信度**仍会画进图里** ——
它们会让 1644 年在任人数虚高，而使用者从图上分辨不出哪些是南明。
**宁可少画，不可误导。**

**代价**：1644 年的数据不完整（只到三月）。前端以「三月城陷」竖线明示断点。

## D16. 时间轴：每年 12 个月等宽；皇帝行置顶；只保留一条时间轴

**背景**（2026-10-16 老板反馈）：

> "皇帝这一行应该在最顶上，你怎么跑到最下面了？"
> "你这时间轴有两条，非常复杂，还是简洁一点好了"
> "还是每年都要有12个月的刻度，每年的长度要一样，这样美观一点，跑起来也比较直观"

**决策**：

1. **皇帝行置顶** —— 原来错放在表格最底；它是"背景坐标"，理应在所有职官之上；
2. **只保留一条时间轴** —— 原来页头一个滑块条 + 图表内一个年轴，重复且混乱。
   现在：滑块留在页头属"视图控件"，**年轴并入图表**（与表格同处一条轴上，
   所以必然对齐、也必然一起滚动）；
3. **按月等宽**：每年固定 12 格，17 年 = 204 格。各年长度完全一致。
4. **去掉虚岁等花活** —— 老板明示"不用管虚岁这些"。

**理由**：按月等宽后，月份精度能落在**正确位置**（五月初任画在 5/12 处），
而不是"整年一条"；且各年等长不会让人误以为某年"更宽"。这是可验证的数学性质，
已用 `tests/test_timeline.py`（25 个测试）钉住。

**代价**：年格变窄（约 18px/年），干支无法逐年标注 —— 改为只在元年/十年/末年显示。

## D17. 断限写法：直接截断到 1644 年 3 月，不加"城陷"之类的主张

**背景**：老板指出：

> "你不要多做主张写一个'城破'，直接写1644年3月，截断一下就好了后面都不要了。
>  崇祯不是这个时候就死了吗？他怎么还会继续？"

**决策**：

1. 去掉上一版「三月城陷」的文字标记，只留一条**断限虚线**，标注值就是 `1644.3`；
2. **所有记录的终年**截到 1644 年 3 月 —— 包括**崇祯本人**。
   他在 1644 年 3 月死，此后不可能仍在位；数据里若 end 是 1644（整年），
   截断后即为 1644-03；
3. 截断时打 `end_clamped=True` 标记，**区分"史料记为 3 月"与"因断限截到 3 月"** ——
   否则前端会把截断产物当成"史料精确到月"，那是虚报精度。

**理由**：老板的第二问点出一个真问题 —— 皇帝行原本画到 1644 年底，
等于宣称"崇祯在死后仍在位"。**断限必须对皇帝也生效。**

## D18. 月份数据来源：中研院明实录（更正上一版结论）

**背景**：我上一版写"月份不可得"，老板指出「《明实录》里面就有就任月份的」。

**核实结果：老板说得对，我错了。** 月份在检索结果的**出處列**：

```
明實錄 附錄 崇禎實錄 卷十 崇禎十年 五月
                            └──── 年号纪年含月 ────┘
```

实测覆盖率 **35/35 = 100%**（修正闰月漏检后）。

**决策**：
- 解析逻辑固化进 `src/mingoff/shilu.py`，测试用**真实返回**做样本；
- demo 当前已接入（2026-10-16）：解析器 + 回填 + 抽屉贴实录原文；
  **关键发现：完整结果藏在 `out` 隐藏字段的 base64 里**，只解析可见表格
  会丢 93% 的数据（详见 `demo开发经验总结.md` 第三节）；
- 详情抽屉明确区分"史料真记了月份"与"因断限截断"，不混为一谈。

## D19. 无限画布：月格等宽横向铺开，页头 fixed（2026-10-16）

**背景**：demo 一期把 17 年压缩进一页，月份格挤成一团（老板反馈"无限画布，
不必拘束一页……每个月也清楚"）。

**决策**：画布改为月格等宽横向铺开（195 月格 × 26px ≈ 5200px），页头/滑块
`position:fixed` 钉视口，图表区 `padding-top` 补偿；所有几何元素（条/线/格）
**统一用像素定位**（格号 × SLOT_W），废弃百分比。

**理由与代价**：sticky 在 body 撑开前无效、100vw+clip 会卡死滚动、百分比与
像素混用差一个标签列宽——三个坑的完整分析见 `demo开发经验总结.md` 第一节。
统一坐标系后断限线与条末端 1px 内对齐（此前三轮都没修对，根因就是单位混用）。

## D20. 月份回填纪律：同年唯一记录才回填（2026-10-16）

**背景**：实录命中 ≠ 就任记录。一个检索词一年可命中十几条（升迁/调任/议事）。

**决策**：脚本只回填"某人某年恰有一条带月记录，且该年恰是 tenure 起迄年"的情形，
打 `*_from_shilu` 标记；同年多月（167 处）一律不回填，留人工校勘。闰月不设独立格，
记入同名平月格 + `*_leap` 字段留证（评估详见 `demo开发经验总结.md` 第五节）。

**代价**：起月覆盖 33%。**收益**：零编造。阶段②逐条校勘后预计 70%+。
