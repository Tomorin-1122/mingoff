## 一、先回答"是不是打开方式不对"

**不全是。** 上一轮的问题一半是我的调用姿势，一半是模型本身的边界。分开说：

| 我犯错的地方 | 现象 | 修正后 |
|---|---|---|
| 问句里写判据 | 加定义反而把准确率带偏 | 判据放进 **choice 的选项描述**，问句保持中性 → 效果显著变好（见 3.1） |
| 问题 id 带前缀 | `answers` 静默丢键 | 用短 id（`is` / `how` / `k`），并校验非空 |
| terms 写成数组 | 400 `criteria` 必须是 dict | `choice` 必须 `{选项: 描述}`，数组会直接 400 |
| 一次问太多角度 | 结果互相打架 | 一次只问 1–3 个**同向**问题最稳 |

**模型本身的天花板（改姿势也绕不过）**：
- 它是**文本判别器**，不是**知识库**（"正德帝叫什么"答错，见第一篇）；
- 它按**字面**判，不按**史实**判（把人名换成"某甲"结果不变）；
- 它**不懂明代制度**（"御史臺/都察院"分不清，"兼銜 vs 陞遷"分不清）。

## 二、真实长板（修正姿势后）

### 2.1 choice + 选项描述 = 它的正确用法

同一段任命文本（"以大明會典成陞纂修官…俱為學士"），换 5 种选项表，**答案全部稳定**：

| 选项表 | 结果 | 置信度 |
|---|---|---|
| 4 项 / 4+其他 / 7 项细分 / 11 项 | 全部 `任命-入` | 0.93–0.96 |
| **二选一**（任职史料 / 非任职史料） | `任职史料` | 0.98 |

选项从 2 个加到 11 个，答案不飘。**这比 `noul` 稳得多**——`noul` 换个问法能飘 0.44（见 2.3）。

### 2.2 指令遵循：能按我给的定义走

同一文本、同一问句，只换选项描述（含/不含"赏赐"档、12 档细分）：

```
D0 仅键名      → 人事记载 0.89
D1 原描述      → 人事记载 0.99
D2 加赏赐档    → 人事记载 0.98
D3 加其他档    → 人事记载 0.95
D4 12档细分    → 人事记载 0.95
R  反向引导（硬塞"赏赐"档描述）→ 人事记载 0.88
```

**答案一次没变，连引导也没带偏。** 结论：**在文本足够明确时，它是守规矩的**；
上一轮"给标准反而判错"的问题出在 `noul` + 问句内定义，不在模型本身。

### 2.3 问法敏感度（这是 `noul` 的真毛病）

同一段明确任命，8 种问法：

| 问法 | P(yes) |
|---|---|
| A 中性 | 0.93 |
| B 带引导词 | 0.99 |
| **C 否定式**（问"是否不是任职史料"） | **0.55** |
| D 长定义 | 0.95 |
| E 短问 | 0.99 |
| F 要求严格 | 0.90 |
| G 提示常见错误 | 0.94 |
| H 二选一前置 | 0.99 |

除 C（否定式把概率意思反转了，用了才知道）外，其余 0.90–0.99，**一致**。
**结论：别用否定式问句，别在问句里塞判据。**

### 2.4 文档 + 指令 + 逐条判断（mini agent 形态）可用

给它一个 JSON：任务说明 + 两条实录记录。问"r0 是否支持李东阳 1488 任内阁大学士"：

```
r0「○命禮部右侍郎兼翰林院侍讀學士李東陽充經筵講官」→ 0.40
r1「○大學士李東陽等言今日天氣亢旱乞減膳」        → 0.20
```

**答对了方向**（都没直接证明"任大学士"）。但 r0 里明明有"礼部右侍郎"这个实职，它没有区分
"任职"与"任大学士"——**判的是模糊的"支持不支持"**。用文档形态可以，但问题必须设计到"是/否"级别。

### 2.5 自洽性：一次 7 问互不矛盾

同一段任命，一次请求 7 问：

```
记任免 0.98 / 有具体官职 0.50 / 有任免动词 0.99 / 是奏疏 0.00 / 是礼仪 0.01
分类 choice=任命 0.97 / 明确度 score=2.57（3=非常明确）
```

内部**不打架**。但"有具体官职 0.50"明显低于文本事实（"翰林院学士"实实在在），
说明**细粒度事实问题会掉分**，粗粒度可以。

## 三、省钱账：这才是它真正值钱的地方

### 3.1 一次请求可以挂多个问题，成本几乎不按问题数涨

同一段 200 字文本：

| 问题数 | input_tokens | 服务端耗时 |
|---|---|---|
| 1 | 226 | 43 ms |
| 5 | 295 | 59 ms |
| 10 | 368 | 83 ms |
| 16 | 467 | 103 ms |

**16 个判断 = 467 tokens**，比 5 次单问（每次 ~226）省一半多。

### 3.2 和生成式模型比

| | 决策模型 | 生成式（qwen-plus 级） |
|---|---|---|
| 输出 | **0 token** | 需生成 JSON + 解释，几百 token 起 |
| 16 个判断 | 467 input tokens | 同样 16 个判断要生成 16 段 JSON，且易格式错 |
| 价格 | 现在**限时免费**（北京/新加坡），原价待定 | 按输出计费 |

**真正省钱的场景**：**对海量文本做结构化打标**。例如给 27,544 条实录每条打 5 个标签
（是否任职/是否奏疏/是否灾异/是否祭祀/明确度）≈ 每条 300 tokens，
全库约 830 万 input tokens（27,544 条 × 平均 114 字 × 7 标签 ≈ 302 tok/条）。如果输出按生成式算，同等信息要多付 10 倍以上。

### 3.3 但注意：上限 1,200 RPM / 200 万 TPM

27,544 条按每条 302 tokens ≈ 830 万 tokens，**一分钟才 200 万**，全库打标至少 6 分钟纯限流，
实际含重试约 20–30 分钟。免费期可以跑，正式价要看原价。

## 四、到底该怎么用（给项目的落地建议）

| 用途 | 姿势 | 价值 |
|---|---|---|
| **实录条目打标**（5–8 个 choice 标签，一次请求） | 选项描述写清标准，问句中性 | ✅ 最实在，直接可用于 site 检索筛选 |
| **任职史料二分类（粗筛）** | 二选一 choice，不用 noul | ✅ 作为规则命中的**前置过滤器** |
| **抽样质检队列** | 用 `score` 打"明确度"，挑低分的回原书看 | ✅ 省人工 |
| **替代注文解析 / 主体归属** | — | ❌ 做不到（把人名换掉结果不变） |
| **明代制度判断**（衙署归属、兼衔/陞遷、年号换算） | — | ❌ 做不到 |

## 五、一句话

**"宣传牛"不假，但牛的是「一次前向、多题并答、零输出、低延迟」的工程属性，不是「懂明代」的学术能力。**
把它当**批量打标机**用，值；当**史实裁决器**用，会翻车。
